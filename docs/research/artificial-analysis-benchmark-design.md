# Artificial Analysis ideas for the ResearchPi benchmark

Verified: 2026-10-04. Scope: official Artificial Analysis methodology and evaluation pages. This is design research, not an Artificial Analysis benchmark replication or a measured ResearchPi result. The proposed comparison is between Pi SDK profiles `pi`, `pi-research`, and `repi` using the same DeepSeek V4.1 Flash endpoint through OpenCode Go; the configuration supplied by the project must still be recorded and checked at execution time.

## Verified source observations

- **Broad intelligence is different from task-specific capability.** The current Intelligence Index v4.3.2 combines ten evaluations under Agents, Coding, Scientific Reasoning, and General categories. Its methodology describes primarily English text evaluation, generally uses pass@1, and reports a composite confidence interval estimate below ±1% from repeated experiments while warning that individual evaluations can be less certain. Default sampling differs for reasoning and non-reasoning models and permits creator recommendations. AA-Briefcase grades file deliverables on task success, analytical quality, and presentation. These are useful axes; their weights and uncertainty do not transfer automatically to our benchmark. [Intelligence methodology](https://artificialanalysis.ai/methodology/intelligence-benchmarking)

- **Use-case indexes require explicit choices.** Artificial Analysis publishes profession-specific capability indexes with different weights for knowledge, reasoning, agentic work, long context, and non-hallucination. The weights reflect the intended work mix rather than a universal measure of competence. [Capability indexes](https://artificialanalysis.ai/methodology/capability-indices)

- **An agent row describes an entire variant.** Coding Agent Index v1.5 separates repository implementation, terminal execution, and repository Q&A. It averages three attempts per task and then tasks; reports token use, cost, and wall-clock time; excludes missing telemetry from metric averages; and treats behavioral settings as separate variants. It also describes checks for manipulation of verifiers and retrieval of published answers. These coding results cannot establish performance on literature review or scientific interpretation. [Coding agent methodology](https://artificialanalysis.ai/methodology/coding-agents-benchmarking)

- **A controlled swap measures added capability.** Search API Bench holds the answer model and task fixed, changes the search provider, and includes a model-only baseline. It combines exact-answer accuracy, answer-set F1, and factual QA accuracy, uses bounded agent turns, and filters benchmark leaks. Interpretation considers quality uplift, added cost, added latency, and consistency across task families. Its source distinguishes recoverable fetch failures from fatal provider errors. [Search API methodology](https://artificialanalysis.ai/methodology/search-api)

- **Latency has several meanings.** API benchmarking separates first token, first answer token, post-first-token output speed, and complete-response time. Its tests span multiple context sizes and sequential/parallel load, use fresh diverse prompts, and summarize repeated measurements with medians. Standardized `o200k_base` text counts support throughput comparison; provider-reported native counts support billed usage. Location affects latency and output type affects speed. [API performance methodology](https://artificialanalysis.ai/methodology/performance-benchmarking)

- **Price, usage, and endpoint identity are separate.** Artificial Analysis distinguishes model creator, hosting provider, and endpoint. Its blended price assumes a cache/input/output mix of 7:2:1; cost per task instead reflects workload consumption. First token can be a reasoning token. Thus a cheap token price does not imply a cheap completed task. [General methodology and definitions](https://artificialanalysis.ai/methodology)

- **Decode time is not task wall time.** The model leaderboard defines its time per Intelligence Index task as output tokens divided by measured output speed, weighted across evaluations; its label explicitly excludes TTFT and overhead. This is a derived inference estimate. [Model leaderboard metric definitions](https://artificialanalysis.ai/models/)

- **Agent workload shapes matter.** AA-AgentPerf uses variable-context, multi-turn trajectories with tool delays and sustained concurrency. It evaluates per-request tail latency and lower-percentile output speed against service targets. It is an inference hardware/deployment benchmark, not a research-quality test. [AA-AgentPerf methodology](https://artificialanalysis.ai/methodology/agentperf)

## Eight proposed ResearchPi adaptations

All items below are project-specific proposals inferred from the observations above. They are not claims that Artificial Analysis uses these ResearchPi tasks, rubrics, thresholds, or statistical procedures.

1. **Compare profiles while fixing the inference configuration.** Resolve model ID, provider ID, endpoint/base URL identifier, reasoning setting, sampling parameters, token limits, SDK/package versions, profile prompt hashes, and tool availability before running. Store this manifest beside results. Run all profiles on the same task instances and source snapshots with equal runtime and usage caps. Disable fallback to another model or label a fallback run as a different variant. The primary estimand is the difference between profiles under this endpoint and budget, not general model intelligence. Add a direct model-only/no-tools diagnostic later if useful; it is distinct from the `pi` agent baseline.

2. **Report a research scorecard before a composite score.** Use task families for source-grounded synthesis, numerical analysis, reproducibility/artifact production, uncertainty/error identification, and research planning. Publish correctness, source support, completeness, uncertainty handling, and artifact reproducibility separately. Include unsupported factual claims and fabricated citations as explicit penalties or failed criteria. Presentation can be reported independently so readable prose does not compensate for incorrect analysis. If a headline score is required, freeze and disclose weights before validation runs and retain the component scores.

3. **Grade submitted artifacts with evidence.** Require exact output paths and a finish record; grade the actual files in an isolated verifier. Prefer deterministic numerical/schema/reproducibility checks for objective requirements. For synthesis, check whether each claim is supported by supplied evidence and whether citations resolve to the claimed passage. Any subjective judge should be versioned, blinded to profile identity, and given the same task-specific rubric; preserve criterion decisions and evidence. Missing required artifacts, budget exhaustion, and invalid output are visible failure states, not successful completion because the final chat message sounds plausible.

4. **Use independent repeated attempts and paired analysis.** Start a pilot with three independent attempts per task/profile, resetting workspace and conversation state each time. Average repeats within task, then macro-average tasks or prespecified families. Pass@1 means the expected success of one attempt; it must not mean selecting the best of three. Compute profile differences on matched tasks and estimate uncertainty by resampling tasks as clusters, keeping their repeats together. Publish per-task results, sample size, interval method, and failure rates. With a small pilot, describe differences as exploratory; do not borrow AA's ±1% claim or declare a winner from tiny gaps.

5. **Measure wall-clock completion and preserve inference timing separately.** The primary runtime is task start to valid submitted artifacts, including model calls, tool execution, queues, retry backoff, and profile overhead. Also store per-call TTFT, time to first answer, complete-response time, and tool duration when observable. Report medians and an explicitly chosen tail percentile only when sample size supports it. Mark unavailable stream timing as unavailable. Do not reconstruct task wall time from output tokens/throughput. Interleave profile order across repeat blocks to reduce time-of-day endpoint effects; log concurrency and host environment.

6. **Budget native usage; price costs with an auditable snapshot.** Store API-reported input, cache-read, cache-write, reasoning, and output counts without assuming that all providers expose disjoint categories. Record missing fields and avoid double-counting reasoning included in output. Enforce comparable wall-time and token/usage limits; separately track tool-call charges and all retries. Save pricing date and category rates for a derived pay-per-token estimate. OpenCode Go subscription expenditure and a comparable API-cost estimate are different quantities: label them separately and leave costs unknown when rates or usage are unavailable. Avoid applying a generic 7:2:1 blended price to measured runs. Report cost per attempted task and cost per successful task with denominators.

7. **Separate development tasks from generated validation tasks honestly.** Use known development fixtures to debug the runner and rubric. Freeze profiles, budgets, grader, generator version, source pool, and selection rules before selecting validation seeds/instances. Publish generator and seed provenance. Describe publicly reproducible instances as generated validation, not a secret or contamination-proof holdout. Keep reference outputs and verifier execution outside agent-readable workspaces, restrict benchmark-answer retrieval, and preserve trajectories for audit. A public generator can still expose task structure; it does not establish resistance to training contamination or broad external validity.

8. **Publish quality–time–cost trade-offs and a failure taxonomy.** Plot or tabulate each profile's paired quality difference, task runtime, native usage, and estimated cost. Report provider/API failures, tool failures, parsing errors, invalid artifacts, time/usage exhaustion, and rubric failures separately. Freeze retry rules before evaluation, never retry merely to improve correctness, and include retry consumption in totals. Show completed-attempt quality alongside all-attempt success so infrastructure issues do not silently disappear. A defensible conclusion is “under these tasks and budgets, profile X changed these measured outcomes”; broader research readiness requires more domains, realistic source corpora, and independent validation.

## Minimal pilot result record

One record per task × profile × repeat should include the resolved manifest; task/generator/source hashes; start/end timestamps; termination reason; model/tool event counts; native usage and missing-field flags; retries; artifact paths/hashes; criterion scores and evidence; pricing snapshot or cost-unavailable reason; and verifier/grader version. Preserve raw events for audits while redacting credentials. These fields support the proposed analysis; adding a field alone does not verify that the runner captures it correctly.

## Limits of this review

Official pages were read live on the verification date, and their versions can change. No private evaluation dataset, full judge reproducibility study, or AA execution logs were inspected. This note borrows measurement principles rather than reproducing published rankings. None of the cited sources establishes a ResearchPi advantage, proves the validity of a custom rubric, or guarantees that a publicly generated validation set is unseen.
